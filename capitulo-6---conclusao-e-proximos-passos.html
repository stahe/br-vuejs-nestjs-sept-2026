    7. Capítulo 6 - Conclusão e próximos passos

    7.1. O que foi construído

    Este documento adaptou o núcleo funcional e a autenticação da aplicação [RdvMedecins] do documento original de 2014 para tecnologias atuais:

    • um servidor [NestJS] completo (entidades [TypeORM], DAO, camada de negócio, camada web), expondo as mesmas 11 rotas de negócio (JSON) do servidor Spring 4 original, na mesma porta (8080), todas agora protegidas por um token (JWT);
    • uma camada de autenticação ([@nestjs/passport] + [@nestjs/jwt]): autenticação por login/senha (POST /login), um token assinado apresentado a cada requisição seguinte e controle de acesso baseado em papéis ([@Roles]('ADMIN') + [RolesGuard]) nas duas rotas que modificam dados;
    • um cliente [Vue.js] (Composition API, setup script) que oferece as mesmas funcionalidades do cliente AngularJS 1.x original—seleção de um médico e de uma data, visualização da agenda, reserva e cancelamento de uma consulta—complementado por uma tela de login, uma sessão persistente (localStorage), uma interface Bootstrap que se adapta ao papel do usuário conectado (botões de agendamento ocultos para o papel USER) e a possibilidade de alternar a interface entre francês e inglês ([vue-i18n]).

    O núcleo do banco de dados não mudou (as mesmas tabelas [doctors/clients/slots/appointments], as mesmas restrições), exceto pela adição da tabela [users]; a arquitetura geral em camadas também não mudou—apenas as ferramentas que a implementam foram atualizadas.

    Há duas diferenças intencionais em relação ao processo de autenticação do documento original, documentadas em detalhe no Capítulo 3: um token JWT em vez do cabeçalho HTTP Basic enviado a cada requisição, e uma única coluna [role] por usuário em vez de uma relação muitos-para-muitos entre três tabelas. Uma terceira diferença—esta funcional—foi escolhida deliberadamente para este port: o papel USER agora pode visualizar as agendas (somente leitura), ao passo que no original servia apenas para ilustrar uma negação total de acesso.

    7.2. O que fica fora do escopo ou a ser portado

    Além do que foi apresentado, o documento original abordava dois temas adicionais—um dos quais já foi tratado, outro deliberadamente deixado de fora, e o terceiro adiado para uma etapa posterior:

    7.2.1. Internacionalização francês/inglês—tratada neste documento

    O documento original propunha alternar a interface entre francês e inglês usando a biblioteca [angular-translate]. Este port implementa essa funcionalidade usando seu equivalente no ecossistema [Vue.js] atual, [vue-i18n] (cujos dicionários fr.json/en.json são carregados por HTTP a partir da pasta [public/i18n/] por meio de uma pequena função de carregamento escrita para este port, já que não existe um plugin HTTP oficial equivalente ao usado no lado React) - Veja o Capítulo 5. Como o [angular-translate] antes dele, [vue-i18n] permite alternar os idiomas em tempo real, sem recarregar a página—um comportamento fiel ao do documento original.

    7.2.2. O modo “debug” do cliente—deliberadamente excluído do escopo

    O documento original incluía um modo de exibição técnico, ativável pela interface, que dava acesso ao modelo bruto ($scope do AngularJS 1.x) da view atual—um recurso útil em 2014, quando as ferramentas de desenvolvimento disponíveis para inspecionar uma aplicação AngularJS ainda eram limitadas. Este port não o recria: as ferramentas de desenvolvimento [Vue.js] atuais ([Vue.js] DevTools, extensão oficial do navegador) oferecem hoje, fora da própria aplicação, uma inspeção muito mais completa dos componentes, de seu estado e de suas props do que ofereceria um painel de depuração personalizado reintegrado à interface. Adicionar esse painel equivaleria a criar uma versão inferior de uma ferramenta já fornecida pelo ecossistema—esta decisão é, portanto, definitiva, e não um mero adiamento.

    7.2.3. Atraso de rede artificial—adiado

    O documento original permitia definir um atraso artificial antes de cada resposta do servidor, para observar o comportamento da interface em uma rede lenta (indicadores de carregamento, desativação temporária de botões etc.). Este recurso ainda não tem equivalente neste port.

    7.3. Uma observação sobre a metodologia usada neste documento

    Este documento foi escrito com base inteiramente no código que foi realmente executado: cada rota do servidor foi testada (incluindo os cenários de autenticação: login bem-sucedido/malsucedido, acesso sem token, acesso com o papel errado), e cada captura de tela do cliente (Capítulo 5) foi obtida interagindo com a aplicação real em execução—um navegador Chromium controlado automaticamente, usando os dados de demonstração do script SQL fornecido. Essa abordagem também revelou, durante a preparação deste documento, um problema específico quanto ao uso do [TypeORM] com colunas calculadas ([@RelationId])—que foi relatado e corrigido no Capítulo 3, diretamente no código entregue. Essa exigência também explica por que as capturas de tela do Postman não foram simuladas: essa etapa ficou a cargo do autor do documento, que as criou diretamente a partir de sua própria estação de trabalho (veja o Capítulo 1).

    7.4. Para ir mais longe desde já

    Enquanto se aguardam as próximas etapas deste port, o servidor e o cliente incluídos neste documento oferecem uma base pronta para uso, para você experimentar por conta própria:

    • adicionar um novo médico ou um novo paciente (atualmente, isso só pode ser feito modificando o script SQL—uma rota chamada /addDoctor, também protegida por [@Roles]('ADMIN'), poderia ser um bom primeiro exercício);
    • adicionar um terceiro papel, ou um usuário com vários papéis—uma oportunidade de avaliar, de forma bem concreta, o custo de abandonar a simplificação da coluna única oferecida por [role] (veja o Capítulo 3);
    • modificar a apresentação do cliente (cores, layout) sem alterar o servidor—uma boa maneira de verificar se a arquitetura em camadas do cliente funciona como anunciado;
    • Leia o arquivo README de cada pasta do servidor e do cliente entregues: cada um explica, em seu contexto, o papel dos arquivos que contém.
